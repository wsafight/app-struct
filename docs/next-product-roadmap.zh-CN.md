# AppStruct 下一阶段产品路线图

> 状态：正在实现（Phase A 已完成；Phase B 的正确性与运维工作大体完成）
> 日期：2026-08-30
> 范围：M0-M6 技术预览基线之后的产品工作

## 1. 结果

AppStruct 已经拥有可靠的应用编译器、迁移工作流、生成的 REST API、React CRUD 运行时、认证、租户隔离、审计、邮件、jobs 和文件模块。下一产品阶段应让这些基础能力对现有数据库和重复性运维工作更有用，而不是扩展所支持的技术矩阵。

推荐顺序是：

1. 现有数据库接入和更丰富的数据访问。
2. 高频管理工作流和运维控制台。
3. 自动化、分发、部署和可视化工具。

GraphQL、额外数据库、运行时加载的 Rust 插件以及面向 CMS 的页面构建器不是近期优先级。查询能力应首先表示在共享 IR 中，以便 REST、OpenAPI、生成的客户端以及任何未来的协议适配器保留相同的授权规则。

## 2. 产品缺口

### 2.1 现有数据库接入

只读的 `appstruct db pull` 工作流现在可以从 PostgreSQL 派生可审阅的 App Spec 草稿。剩余缺口是从真实世界 schema 迁移：复合键和跨 schema 关系仍需手工建模。Domains 会作为其基础标量导入并带约束警告；数组、生成列和不支持的类型会被省略并给出警告，而不是发出运行时不兼容的字段。访问规则无法从数据库元数据推断。

### 2.2 数据访问与报表

生成的资源现在提供偏移/游标分页、一跳关系过滤器、有界聚合/分组以及字段级访问。剩余缺口是只读计算字段、更深的关系遍历、更丰富的报表/仪表盘查询，以及带用户选定排序键的游标遍历。

### 2.3 管理效率

Web 运行时现在具有显式批量操作、已保存视图、导入/导出、软删除、恢复、修订安全的行内标量编辑，以及带字段级差异的审计历史。剩余效率缺口是记录范围的历史导航，以及更完整的可复用无头表单/URL 控制器，供自定义页面使用。生成的列表/详情页和自定义页面 props 现在共享第一片无头控制器，用于查询键、权限门、请求状态、重新获取和变更失效。

### 2.4 运维管理

已实现的模块暴露了基础设施能力，但运维 UI 有限。Admin 模块应在把 Billing 加入 SaaS 预设之前，完成组织/会话操作、邮件捕获、文件使用以及记录范围的审计导航。

### 2.5 自动化与生态

Jobs outbox 是 schedules、数据库变更事件、签名 webhooks、重放以及服务端推送更新的自然基础。第三方模块应在构建时下载并校验，带锁定校验和与兼容性契约。生产运行时加载动态 Rust 库仍不在范围内。

### 下一份契约冻结

下一片数据和 Web 运行时必须在实现之前确定其公共契约：

1. 计算字段使用类型化、可移植的 IR 表达式，而不是在 App Spec 中嵌入未检查的 SQL。契约必须在向 schema 添加语法之前定义受支持的运算符、空值传播、字段依赖和读访问行为。
2. 已排序的游标令牌绑定有序排序规格和类型化键值，定义空值排序，并始终把主键作为最终平局打破项。来自不同过滤或排序契约的游标必须被拒绝。
3. 服务端已保存视图记录所有者、资源、受修订保护的查询状态，以及 `private` 或租户范围的 `team` 可见性。团队视图可由创建者写入、由组织读取；在租户模式之外，仅提供私有和浏览器本地视图。
4. 无头控制器只有在拥有 URL 查询解析以及表单校验、字段错误、修订冲突和未保存变更状态时才算完整。生成页面和自定义页面必须消费同一控制器契约。

游标模式仍按主键排序，自定义表单继续拥有自己的表单和 URL 状态。

## 4. 第一片：`appstruct db pull`

### 4.1 命令契约

```text
appstruct db pull [--schema public] [--output spec/imported.yaml] [--check | --diff]
```

该命令：

- 发现现有 AppStruct 项目；
- 从进程环境或项目 `.env` 读取 `DATABASE_URL`，进程值优先；
- 使用与迁移命令相同的 TLS 策略连接；
- 只执行 PostgreSQL catalog 读取；
- 写入确定性的领域 Spec 草稿；
- 选择 `--check` 或 `--diff` 时比较现有草稿而不写入；
- 拒绝绝对输出路径、父级遍历、符号链接和已有目标；
- 不更改 `appstruct.yaml`、`includes`、迁移、快照、锁或生成文件。

机器可读输出使用标准成功/错误信封，并报告 schema、输出路径、表/实体数量和警告。

### 4.2 第一版支持的形状

- 一个显式选定的 PostgreSQL schema 中的基表。
- 每个生成实体恰好一列主键。
- UUID、character、text、integer、bigint、decimal、boolean、date、timestamp、JSON/JSONB 以及原生 PostgreSQL enum 列。
- Identity/serial 整数生成和当前时间 timestamp 默认值。
- 单列唯一约束。
- 指向所选 schema 和生成实体的单列外键。
- `RESTRICT`/`NO ACTION`、`CASCADE` 和 `SET NULL` 删除行为。

带引号的数据库标识符会被规范化为可移植的 AppStruct 名称，同时通过显式 `table` 和 `column` 声明保留原始表或列。

### 4.3 需要审阅的形状

复合主键、复合外键和跨 schema 关系会作为警告报告。Domains 会降为受支持的基础标量并带约束警告。数组、生成列、表达式和不支持的 PostgreSQL 类型会被省略并给出警告。没有恰好一列主键的表会被省略，因为 AppStruct 实体需要单个键。草稿永远不会自动加入 `includes`。

访问规则无法从数据库 schema 推断。生成的实体故意省略 `access`，因此在开发者声明 public、authenticated、role 或 owner 策略之前，把草稿加入应用会失败关闭。

### 4.4 验收标准

1. 将同一未更改的数据库两次拉取到不同路径会产生相同字节。
2. 典型的 UUID 父子 schema 会渲染有效的实体、字段、枚举、唯一、generated 和关系声明。
3. 缺失 `DATABASE_URL`、连接失败、无效 schema 名、不安全输出路径和已有文件会失败且不发生文件系统变更。
4. 不支持的数据库形状产生确定性警告，且不暴露连接 URL。
5. 文本和 JSON 命令模式遵循现有 CLI 契约。
6. 单元测试覆盖 catalog 到模型的映射和渲染；当仓库数据库测试环境可用时，PostgreSQL 集成测试覆盖该命令。
