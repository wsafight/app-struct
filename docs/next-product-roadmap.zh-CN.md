# AppStruct 下一阶段产品路线图

> 状态：正在实现（Phase A、Phase B 已完成；Phase C 只推进有用户证据的交付能力）
> 日期：2026-10-28
> 范围：M0-M6 技术预览基线之后的产品工作

## 1. 结果

AppStruct 已经拥有可靠的应用编译器、迁移工作流、生成的 REST API、React CRUD 运行时、认证、租户隔离、审计、邮件、jobs 和文件模块。首要产品入口固定为“现有 PostgreSQL 到带权限、审计和运维界面的安全管理应用”。下一阶段应提高这条旅程的完成率，而不是扩展所支持的技术矩阵。

推荐顺序是：

1. 现有数据库接入和更丰富的数据访问。
2. 高频管理工作流和运维控制台。
3. 自动化、分发、部署和可视化工具。

GraphQL、额外数据库、运行时加载的 Rust 插件以及面向 CMS 的页面构建器不是近期优先级。查询能力应首先表示在共享 IR 中，以便 REST、OpenAPI、生成的客户端以及任何未来的协议适配器保留相同的授权规则。

## 2. 产品缺口

### 2.1 现有数据库接入

`appstruct db pull` 工作流现在可以从 PostgreSQL 派生可审阅的 App Spec 草稿；`--review` 会在终端中逐表展示字段和关系、确认导入表并在写入前列出警告。剩余缺口是从真实世界 schema 迁移：复合键和跨 schema 关系仍需手工建模。Domains 会作为其基础标量导入并带约束警告；数组、生成列和不支持的类型会被省略并给出警告，而不是发出运行时不兼容的字段。访问规则无法从数据库元数据推断。

显式 `migrate baseline` 已可在只读比较后登记匹配的标准初始迁移，不执行初始建表 SQL。includes、逐操作权限和 revision 仍需人工审阅；它不自动修复源库，也不接受 seed、自定义 SQL 或迁移链。见[已有数据库指南](existing-database.zh-CN.md)。

### 2.2 数据访问与报表

生成的资源现在提供偏移/游标分页、一跳关系过滤器、有界聚合/分组以及字段级访问。已支持嵌套筛选、字段投影、多列签名游标和按日/周/月的趋势报表。剩余缺口是只读计算字段、更深的关系遍历和跨资源仪表盘。

### 2.3 管理效率

Web 运行时现在具有显式批量操作、已保存视图、导入/导出、软删除、恢复、修订安全的行内标量编辑，以及详情页内带字段级差异和分页的记录历史。列表、详情、自定义页面已共享 URL 和表单控制器，包括字段校验、冲突与草稿状态。导入和批量操作已有预览、逐条结果和失败重试，保存视图也包含报表配置。

### 2.4 运维管理

Admin 已提供用户会话撤销、组织成员和邀请、邮件投递、文件元数据、Jobs、Schedules、Webhooks、Billing 事件和全局审计页面；资源详情页提供记录范围的审计导航。下一运维重点是通过确定性发布清单和 `appstruct deploy verify` 保证 Staging/Production 晋级使用同一套不可变产物，而不是新增另一套通用控制台。

### 2.5 自动化与生态

Jobs outbox 是 schedules、数据库变更事件、签名 webhooks、重放以及服务端推送更新的自然基础。第三方模块应在构建时下载并校验，带锁定校验和与兼容性契约。生产运行时加载动态 Rust 库仍不在范围内。

### 下一份契约冻结

下一片数据和 Web 运行时必须在实现之前确定其公共契约：

1. 计算字段使用类型化、可移植的 IR 表达式，而不是在 App Spec 中嵌入未检查的 SQL。契约必须在向 schema 添加语法之前定义受支持的运算符、空值传播、字段依赖和读访问行为。
2. 已排序的游标令牌绑定有序排序规格和类型化键值，定义空值排序，并始终把主键作为最终平局打破项。来自不同过滤或排序契约的游标必须被拒绝。
3. 无头控制器只有在拥有 URL 查询解析以及表单校验、字段错误、修订冲突和未保存变更状态时才算完整。生成页面和自定义页面必须消费同一控制器契约。

多列签名游标和共享表单/URL 控制器已经实现；管理表格仍默认页码分页与精确总数。

复合键、跨 schema 关系、计算字段和更深关系遍历不会仅因为“真实数据库可能需要”就进入 IR。每项至少需要三个真实项目样本、失败旅程记录、无法通过现有扩展点解决的说明，以及兼容/授权契约草案。证据不足时优先改进 warning、审阅和手工建模指引。

## 4. 第一片：`appstruct db pull`

### 4.1 命令契约

```text
appstruct db pull [--schema public] [--output spec/imported.yaml] [--review | --check | --diff]
```

该命令：

- 发现现有 AppStruct 项目；
- 从进程环境或项目 `.env` 读取 `DATABASE_URL`，进程值优先；
- 使用与迁移命令相同的 TLS 策略连接；
- 只执行 PostgreSQL catalog 读取；
- 写入确定性的领域 Spec 草稿；
- 选择 `--check` 或 `--diff` 时比较现有草稿而不写入；
- 拒绝绝对输出路径、父级遍历、符号链接和已有目标；
- 不更改 `appstruct.yaml`、`includes`、迁移、快照、锁或生成文件。

机器可读输出使用标准成功/错误信封，并报告 schema、输出路径、表/实体数量和警告。

### 4.2 第一版支持的形状

- 一个显式选定的 PostgreSQL schema 中的基表。
- 每个生成实体恰好一列主键。
- UUID、character、text、integer、bigint、decimal、boolean、date、timestamp、JSON/JSONB 以及原生 PostgreSQL enum 列。
- Identity/serial 整数生成和当前时间 timestamp 默认值。
- 单列唯一约束。
- 指向所选 schema 和生成实体的单列外键。
- `RESTRICT`/`NO ACTION`、`CASCADE` 和 `SET NULL` 删除行为。

带引号的数据库标识符会被规范化为可移植的 AppStruct 名称，同时通过显式 `table` 和 `column` 声明保留原始表或列。

### 4.3 需要审阅的形状

复合主键、复合外键和跨 schema 关系会作为警告报告。Domains 会降为受支持的基础标量并带约束警告。数组、生成列、表达式和不支持的 PostgreSQL 类型会被省略并给出警告。没有恰好一列主键的表会被省略，因为 AppStruct 实体需要单个键。草稿永远不会自动加入 `includes`。

访问规则无法从数据库 schema 推断。生成的实体故意省略 `access`，因此在开发者声明 public、authenticated、role 或 owner 策略之前，把草稿加入应用会失败关闭。

### 4.4 验收标准

1. 将同一未更改的数据库两次拉取到不同路径会产生相同字节。
2. 典型的 UUID 父子 schema 会渲染有效的实体、字段、枚举、唯一、generated 和关系声明。
3. 缺失 `DATABASE_URL`、连接失败、无效 schema 名、不安全输出路径和已有文件会失败且不发生文件系统变更。
4. 不支持的数据库形状产生确定性警告，且不暴露连接 URL。
5. 文本和 JSON 命令模式遵循现有 CLI 契约。
6. 单元测试覆盖 catalog 到模型的映射和渲染；当仓库数据库测试环境可用时，PostgreSQL 集成测试覆盖该命令。

## 5. 后续投入的场景证据

2026-10-27 的 baseline、认证限流、主题文案、数据生命周期、业务扩展示例、模板 diff 和前端校验清理已完成，详见[交付优化](optimization-progress.zh-CN.md)。[平台验收](continuous-integration.zh-CN.md)与[真实用户观察](product-journeys.zh-CN.md)的待执行状态分别维护，不将下面的条件性建议作为默认交付阻塞。

| 方向 | 当前边界与投入条件 |
| --- | --- |
| 计算字段、条件校验和复杂数据库 | 条件必填和同实体大小比较已支持，见[表单校验](form-validation.zh-CN.md)；复杂跨记录规则和按状态变化的字段权限仍用扩展代码。复合键、跨 schema 和更深关系遵循前述真实项目样本门槛。 |
| 看板、日历、跨资源仪表盘及完整 i18n | 已有启动时中英文标准文案、业务字段显示名和统一格式化；运行时语言切换、多语言 Spec 和新页面类型仍按重复需求取证。 |
| 文件直传、分片与扫描 | 依据文件大小、吞吐和安全需求设计；当前引用回收不能替代无元数据存储孤儿对账。 |
| Jobs 优先级与通用工作流 | 当前 PostgreSQL Jobs 有命名队列、租约、重试、死信和重放；Workflow 是单实体状态机。先测排队和失败恢复，不凭存储选型推断容量不足。 |
| Redis Session 与数据库 RLS | 用连接池、认证延迟或隔离要求取证。RLS 必须同时设计连接角色、事务、worker 和管理员路径；当前为应用层租户隔离。 |
| 列表总数和聚合成本 | 默认精确 COUNT；分组数量上限不限制扫描成本。使用真实分布、索引和执行计划，再决定估算、超时或分页策略。基准工具支持百万行不代表已完成百万行验收。 |
| 第三方可执行模块 | 远程包已支持静态 Artifact 分发；执行代码前需定义编译、注册、依赖、迁移和卸载契约，不默认引入动态库或 WASM。 |
| 支付、平台适配器、Playground、编辑器、AI/MCP 与托管 | Stripe Billing v1 已有订阅能力；复杂计费和新交付入口按真实项目的重复需求排序。 |

数据库恢复继续优先验证备份还原和前向修复，不要求自动 down SQL。测试优化依据耗时、失败率和重复覆盖；现有 Tenant、Jobs、File、Mail、Billing 的支持范围依据需求和维护成本决定，不按功能数量拆除。
