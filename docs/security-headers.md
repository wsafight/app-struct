# Security Response Headers

Generated backends apply a baseline set of security response headers to every route. The defaults
are on, so a project that never mentions `server:` still ships `X-Content-Type-Options`,
`X-Frame-Options`, and `Referrer-Policy`, and adds `Strict-Transport-Security` when
`APPSTRUCT_ENV=production`.

```yaml
server:
  security_headers:
    enabled: true
    hsts: auto
    frame_options: deny
    referrer_policy: strict-origin-when-cross-origin
    content_security_policy: null
    custom:
      x-robots-tag: noindex
```

## Defaults

| Key | Default | Emitted header |
| --- | --- | --- |
| `enabled` | `true` | — |
| `hsts` | `auto` | `Strict-Transport-Security: max-age=31536000; includeSubDomains`, production only |
| `frame_options` | `deny` | `X-Frame-Options: DENY` |
| `referrer_policy` | `strict-origin-when-cross-origin` | `Referrer-Policy: strict-origin-when-cross-origin` |
| `content_security_policy` | unset | `Content-Security-Policy`, only when configured |
| `custom` | empty | one header per entry |

`X-Content-Type-Options: nosniff` is always emitted while `enabled` is `true`; it has no opt-out.

## Options

- `enabled: false` turns every header off. Configuring `content_security_policy` or `custom` while
  disabled emits warning `AS3108`, because the values would be ignored.
- `hsts` accepts `auto`, `off`, or a non-negative max-age in seconds. `auto` emits the header only
  when `APPSTRUCT_ENV=production`; an explicit number always emits it. `preload` is not generated.
- `frame_options` accepts `deny`, `sameorigin`, or `off`.
- `referrer_policy` accepts `no-referrer`, `same-origin`, `strict-origin-when-cross-origin`, or `off`.
- `content_security_policy` is a literal policy string. It is not generated by default: the Web
  runtime is a single-page application with inline styles, so a useful policy depends on the
  application's own asset and API origins.
- `custom` adds arbitrary headers. Names must be lowercase ASCII letters, digits, and hyphens, and
  values must be visible ASCII or horizontal tabs. Custom headers use `if_not_present`, so they
  never overwrite a header an inner layer already set (CORS, `ETag`).

## Where the headers are applied

The generated `apply_security_headers` helper wraps the whole Axum router, so the headers cover
resource routes, module routes (`/auth`, `/audit`, `/billing`, `/realtime`, `/report`, `/activity`,
tenant routes), `/health/live`, `/health/ready`, `/metrics`, and `/openapi.json`.

Because the layer is outermost, it runs last on the response path. That is what makes
`if_not_present` the right policy for `custom`: a user-supplied `access-control-allow-origin` or
`etag` entry cannot clobber the value the CORS or revision layer produced.
